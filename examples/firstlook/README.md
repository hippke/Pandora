# First-look exomoon screening (example)

A cheap first pass over many transiting-planet light curves. It flags the ones that deserve a full
planet+moon retrieval. It is not part of the `pandoramoon` core: it is an example built on
`pandoramoon.nss` (compiled nested sampler) and `pandoramoon.reparam` (phase-at-transit moon
coordinates), for users to adapt.

## What it does

For one light curve:
1. **Planet-only model:** one short nested-sampling run (7 parameters).
2. **Planet+moon model:** one short nested-sampling run (16 parameters, moon orbit in
   phase-at-transit coordinates).
3. **Output:**
   - the log Bayes factor `dlnz = lnZ(planet+moon) − lnZ(planet only)`;
   - the verdict `interesting = dlnz > threshold`;
   - a rough summary of the moon (period, radius, mass ratio, inclination; median and 16/84 %).

Each model is one run with few live points and short slice chains, without the convergence checks
of `nss.fit`. The evidences are therefore noisy (±0.5) and slightly biased, which is harmless far from
the threshold. **Interesting light curves must be followed up with a full fit** (`nss.fit`, ~10⁹
calls).

```python
import firstlook
fl = firstlook.FirstLook(time, flux, flux_err, t0_bary=11.0, per_bary=(360.25, 370.25), a_bary=(210, 220))
r = fl.run(recall=0.95)            # one light curve on one core (0.90, 0.95, 0.99, 0.999)
print(r["dlnz"], r["interesting"], r["moon"])

results = firstlook.run_many(list_of_firstlooks, threads=16)   # many light curves, one per core
```

All compiled functions take the light curve as an argument. numba compiles once per process
(~30 s), not per light curve.

## Choosing the recall

`fl.run(recall=0.95)` (or 0.90, 0.99, 0.999) picks the cheapest tested setting for the requested
recall of well-detectable moons (reference dlnZ ≥ 8). The knob is not the threshold; it is the
sampler effort:
- a well-detectable moon is missed only when a short moon run never finds the moon's mode;
- that happens in a few % of the runs with 50 live points; no light curve is missed every time
  (worst case 60 %);
- `repeats` independent moon runs, combined as the mean of their Z, all miss with probability
  ~p^repeats.

Several small runs are cheaper than one large one for the same recall. The presets (Round 12;
`recall_study.py --sizes small`, then validated end to end):
- planet run: 50 live points, nsteps 12;
- moon runs: 50 live points, nsteps 8 (0.90, 0.95) or nsteps 16 (0.99, 0.999);
- threshold dlnZ > 3.

Validated end to end (`recall_study.py --validate`, fresh seeds, the 232 moons with reference
dlnZ ≥ 8 and the 240 no-moon light curves of both injection sets; white noise). CPU-s from the
benchmark (`bench_firstlook.py --bench --preset P`, 200 light curves, one core of an AMD Ryzen 9
7950X):

| `recall=` | moon runs | measured recall | misses | false passes | CPU-s / light curve | evaluations | light curves / hour / core |
|---|---|---|---|---|---|---|---|
| 0.90 | 1 × (50 live, nsteps 8) | **94.5 %** | 38 / 696 | 2 / 720 | **0.35** | 0.14 M | ~10 200 |
| **0.95 (default)** | 2 × (50, 8) | **97.3 %** | 31 / 1160 | 1 / 720 | **0.61** | 0.22 M | ~5900 |
| 0.99 | 3 × (50, 16) | **99.84 %** | 3 / 1856 | 2 / 720 | **1.58** | 0.53 M | ~2300 |
| 0.999 | 6 × (50, 16) | **100 %** (95 % upper limit of the miss rate 0.023 %) | 0 / 12 992 | 3 / 1440 | **3.07** | 1.03 M | ~1200 |

- The planet-only model uses the fused planet-only kernel `pandora_loglike_planet` (~2.4× faster
  per call than a dummy moon).
- Moon runs with nsteps 8 are not good enough for 0.99 / 0.999: 3 × and 6 × (70 live, nsteps 8)
  gave only 99.35 % / 99.87 %. Misses of short chains are correlated within a light curve, so
  repeats help less.
- **Retry safeguard:** the moon model (almost) contains the planet-only model. So a moon run
  more than 15 nats below the planet-only run has collapsed onto a wrong solution; up to 2 extra
  moon runs are added in that case.
- For comparison: one moon run with 200 live points (`recall=None`, the first calibration's
  "A") costs ~6 CPU-s; a full checked fit ~3600 CPU-s.

## For publication: setup, injections, cost

**Injected light curves** (`injections.py`; this table is generated by `describe_injections.py`):
- a Sun-like star (R⋆ = R☉, M☉), a Jupiter-like planet (M_p 1.6–2.4·10²⁷ kg), one moon or none;
- circular orbits; impact parameter 0–0.7; limb darkening fixed in the injections (u1 = 0.409,
  u2 = 0.256) and free in the fits;
- moon orbit 0.08–0.45 Hill radii (P_m ≤ 40 d), τ, Ω uniform, i_moon uniform in 0–180° (many
  moons do not transit);
- data = windows around each transit (transit duration + the moon's maximal offset), white
  Gaussian noise of known σ, one sample per cadence (no supersampling; **the injections contain no
  exposure smearing either**, so this calibration does not cover real long-cadence data. In a later test
  (SAMPLING.md, "Supersampling: findings"), fits without supersampling inflated ΔlnZ by +1.7 to +12.6 on
  smeared 30-min data, which could create false detections for high-S/N planets. To be tested for the
  first look (SAMPLING.md backlog item 7); until then use `supersampling_factor=5` for 30-min data);
- S/N = depth × √(in-transit cadences) / σ per cadence. For the moon, its transit is assumed to
  last as long as the planet's.

**Fit setup.** Priors as in the Pandora injection–retrieval notebook:
- per_bary ±1.37 % around the truth; a_bary ±2.3 %;
- R⋆ 0.4–1.2 R☉; r_p 0.07–0.11 R⋆; b 0–1; t0 offset ±0.05 d; M_p 1.5–2.5·10²⁷ kg; q1, q2 0–1;
- moon: r_m 0.01–0.07 R⋆; P_m ≤ 50 d (uniform; sampled as phase at transit); Ω double cover;
  i 0–180°; M_m 0–10²⁷ kg.

The planet-only and the planet+moon models share the priors of their common parameters.

**Labels.** "Well detectable" = a reference run (one nss run per model with 1000 live points,
nsteps 28 / 64; ~17 M evaluations, ~60 CPU-s) gives ΔlnZ ≥ 8. The labels are single runs
(±0.3–0.5 in ΔlnZ), not full checked fits.

**Cost per light curve.** One evaluation of the Pandora likelihood costs 3.1–3.5 µs here (216–1840
cadences; AMD Ryzen 9 7950X, one core). The sampler is compiled together with the likelihood, so
there is no Python per evaluation.

Why it is cheap: a nested-sampling run needs ~n_live × (information H + a few) iterations, each
costing ~nsteps × ~2.7 evaluations. For example, 100 live × ~40 × 16 × 2.7 ≈ 170 k for the planet
run. The price is precision: a single run's logZ error is ~√(H/n), about ±0.6 (planet, 100 live)
and ±1 (moon, 50 live). That suffices for screening: no-moon light curves sit at ΔlnZ ≈ −2.5,
the threshold is 3, and well-detectable moons are at ≥ 8. The posteriors are coarse; the
parameter summary is calibrated (68 % intervals hold 64–68 %) but wide.

## Speed benchmark

Run it after any optimisation of Pandora or nss:

```bash
python bench_firstlook.py --bench --labels cal.jsonl --n-moon 60 --n-null 40 --out /some/dir/bench.jsonl
```

It runs the first look (`--preset 0.95`, default) on a fixed set of 200 injections and appends one line to
`bench_log.jsonl` (next to `--out`):
- CPU seconds per light curve, light curves per hour per core, and calls per light curve;
- the threshold for 2 % false passes, and the recall of well-detectable moons (reference
  dlnZ ≥ 8, from `--labels`).

A speed-up only counts if the recall stays the same.

## Supersampling for detection (`ss_detect.py`, SAMPLING.md backlog 7)

Kepler long-cadence injections with real exposure smearing (`injections.simulate(s, true_ssf=30, fit_ssf=k)`:
the truth averaged over 30 sub-exposures per cadence; the returned time grid is the fit's sub-exposure grid of
factor k), with and without a moon, first look at several fit factors, plus reference fits (1000 live points,
factor 7) that label the detectable moons:

    python ss_detect.py --n-moon 60 --n-null 60 --factors 1,3,5 --recall 0.95 --threads 20 --out ss_detect.jsonl
    python ss_detect.py --summary ss_detect.jsonl     # false positives, recall, dlnZ shift vs factor, CPU-s

`FirstLook(..., supersampling_factor=k)` takes the sub-exposure time grid and the flux / errors at the cadences.
Since Pandora `8b1ce11` the planet-only kernel has a fast path for supersampled cadences.
